# AI 虚拟陪伴 App 框架设计

本文档描述一个面向手机端、无自建服务器的 AI 虚拟陪伴 App 本地架构。所有用户数据、记忆、画像、权限记录和关怀策略默认保存在用户手机本地；用户通过在 App 内配置自己的大模型 API Key 或本地模型进行操作。目标是在轻量化、高质量、可扩展、多模型接入的基础上，让 AI 具备接近真人陪伴的交互体验，支持用户自定义人格、性格、性别、语音、记忆、微信通道、本地实时语音、多设备感知和用户画像沉淀。

## 1. 产品目标

- **高度拟人化陪伴**：支持人格、性格、性别、称呼、说话风格、边界感、情绪表达方式等自定义配置。
- **多模态交互**：支持 App 内文本、实时语音、语音唤醒、微信通道文本/语音回复、蓝牙耳机播放、手机扬声器播放，以及用户确认后的单帧视觉理解。
- **上下文感知**：结合位置、时间、场景音、蓝牙连接状态、智能手表身体数据、用户历史记忆和用户确认后的摄像头画面，智能判断回复方式和内容风格。
- **长期记忆**：每日提取核心事件、用户心情、情绪变化、变化原因，并按日期存储；跨日期相关记忆建立连接。
- **用户画像**：持续沉淀兴趣、生活节奏、情绪模式、关系偏好、沟通习惯、压力来源、重要人物与重要地点。
- **用户自配模型 API**：App 不依赖自建服务器，用户在本地配置 OpenAI、Anthropic、Google、国产大模型或本地模型 API。
- **本地轻量高质量**：移动端承担实时音频、唤醒、打断、播放决策、记忆整理、画像蒸馏和隐私保护；必要时仅把最小化后的请求发送到用户配置的模型 API。
- **跨平台移动端**：同时支持 Android、iOS 和 HarmonyOS，尽量复用业务逻辑，同时尊重三端权限、后台、蓝牙、音频、健康数据和系统安全区差异。
- **低性能影响**：以最小程度影响用户手机性能为原则，保证流畅、稳定、低耗电、低发热、低存储占用和操作简洁。

## 3. 客户端设计

### 3.1 核心模块

1. **聊天 UI 层**
   - 文本输入、消息流、语音消息、情绪卡片、记忆回顾卡片。
   - 支持切换 AI 角色、人格配置、隐私设置、通道设置。

2. **实时语音交互层**
   - 使用流式 ASR 识别用户语音。
   - 使用流式 LLM 输出中间文本。
   - 使用流式 TTS 边生成边播放。
   - 支持用户随时打断：检测到用户说话后立即暂停 TTS，并向本地会话编排器发送 `interrupt` 事件。

3. **权限与设备感知层**
   - 位置权限：用于识别上下文，如通勤、家、公司、旅行。
   - 麦克风权限：用于语音输入、打断检测。
   - 文件管理权限：用于用户主动上传文件、聊天资料、长期个人资料。
   - 蓝牙状态：检测是否连接蓝牙耳机、车载蓝牙、音箱。
   - 智能手表：同步心率、睡眠、运动、压力、血氧等可用数据。

4. **本地对话控制器**
   - 管理会话状态、音频播放队列、TTS 缓冲、网络降级。
   - 在弱网时使用本地轻量模型进行短回复、安抚式回复或离线提示。

### 3.2 播放设备决策

播放策略由客户端实时执行，本地会话编排器只给出建议。

```text
if 当前通道 == 微信:
    if 用户明确要求语音:
        语音回复
    else if 蓝牙耳机已连接 and 当前环境适合语音:
        语音回复
    else:
        文本回复
else if 当前通道 == App 内语音:
    if 蓝牙耳机已连接:
        蓝牙耳机播放
    else if 用户处于公共场景或夜间安静场景:
        降低音量或建议文本
    else:
        手机扬声器播放
else:
    默认文本回复，可提供一键朗读
```

蓝牙设备需要分类：

- **耳机**：默认适合语音播放。
- **车载蓝牙**：适合短语音，避免长篇。
- **音箱**：需要谨慎，默认询问用户是否外放。
- **未知设备**：默认文本，除非用户设置允许。


### 3.3 底层语音监测与语音唤醒

App 底层应有一个低功耗语音监测程序，但它不是持续上传录音，而是在端侧完成唤醒词检测和 VAD。

```text
低功耗音频监听
    ↓
端侧唤醒词检测，例如“小沐”
    ↓
唤醒成功后播放轻提示音或震动
    ↓
开启本地 ASR / 用户配置 LLM API / 本地或 API TTS 语音会话
    ↓
一段时间无语音后自动休眠
```

设计原则：

- 唤醒前音频默认只在本地环形缓冲，不离开手机。
- 唤醒词、VAD、打断检测应尽量使用端侧轻量模型。
- 唤醒后才启用高质量语音识别链路；若调用外部 ASR API，必须展示并遵守用户授权。
- 用户必须能关闭后台语音监测，并查看最近一次唤醒原因。
- 误唤醒后提供“一键删除这段录音/转写”的入口。

### 3.4 智能关怀与打扰判断

App 不能只做“用户提问，AI 回答”的一次性问答。它应在本地维护一个“关怀意图池”，再根据 AI 情绪值、用户情绪状态、身体状态、位置、时间、蓝牙/手表状态、用户忙碌程度和历史偏好，动态判断是否、何时、通过什么通道主动关心。

这不是固定时间的机械闹钟，而是智能触达：

```text
用户早上说：“我今天有点不舒服。”
    ↓
本地情绪与身体状态识别：不适、低能量、需要后续关注
    ↓
写入关怀意图池，不立即固定为某个死时间
    ↓
本地场景循环评估：用户是否在忙、是否睡觉、是否有蓝牙耳机、AI concern 是否升高
    ↓
当“关心价值 > 打扰成本”时再触达；如果场景不合适则延后或静默
```

关怀意图结构：

```json
{
  "care_intent_id": "ci_001",
  "user_id": "local_user",
  "created_at": "2026-06-29T08:30:00Z",
  "reason": "用户早上表达身体不舒服",
  "care_goal": "轻量关心并询问是否好一点",
  "urgency": 0.62,
  "ai_emotion_snapshot": {
    "concern": 0.78,
    "warmth": 0.84,
    "worry": 0.51
  },
  "user_state_snapshot": {
    "emotion": "low_energy",
    "body_signal": "possible_discomfort",
    "confidence": 0.73
  },
  "decision_policy": {
    "trigger_when": "care_value_gt_disturbance_cost",
    "avoid_scenes": ["sleeping", "meeting", "driving", "do_not_disturb"],
    "preferred_channel": "least_intrusive_available"
  }
}
```

本地打扰评分：

```text
关心价值 = 用户不适强度 + AI concern/worry + 事件重要度 + 距离上次互动时长 + 用户偏好
打扰成本 = 睡眠/会议/驾驶概率 + 公共场景外放风险 + 用户忙碌度 + 近期主动触达次数

if 关心价值 - 打扰成本 > 用户设定阈值:
    选择最低打扰通道触达
else:
    延后评估或只在 App 内显示轻提醒
```

主动关怀需要节制：

- 不舒服、强压力、重要事件前后、长时间低落时可以创建关怀意图。
- 用户忙碌、睡眠、会议、驾驶等场景应延后、静默或只做本地提醒。
- 用户可设置主动关怀强度，例如关闭、低频、普通、高陪伴。
- 每次主动触达都要说明来源，例如“你早上说不舒服，我有点担心，想看看你好点没”。


### 3.5 Android、iOS 与 HarmonyOS 支持

App 需要同时支持 Android、iOS 和 HarmonyOS。建议采用“共享业务核心 + 平台原生能力适配”的方式：

```text
共享层
├── 会话编排
├── 人格与 AI 情绪值
├── 记忆与画像逻辑
├── 场景决策
├── 模型网关抽象
└── 智能关怀判断

平台适配层
├── Android：权限、AudioRecord/AAudio、Bluetooth、Health Connect、Keystore、后台限制
├── iOS：权限、AVAudioEngine、CoreBluetooth、HealthKit、Keychain、后台模式限制
└── HarmonyOS：权限、音频采集/播放、蓝牙、运动健康生态、系统安全区、后台任务限制
```

跨平台原则：

- UI 和业务状态可使用跨平台框架，但音频、蓝牙、手表、钥匙串/密钥库、后台唤醒等能力需要平台原生适配。
- Android 重点处理机型碎片化、后台限制、蓝牙设备类型识别、不同厂商省电策略。
- iOS 重点处理后台录音限制、系统权限弹窗、HealthKit 授权、AVAudioSession 与蓝牙路由。
- 三端都要提供清晰的权限说明，并允许用户逐项关闭位置、麦克风、摄像头、蓝牙、健康数据和微信通道。

### 3.6 轻量化与性能预算

这是手机 App，不应为了“拟人化”牺牲用户手机体验。默认策略应是轻量、克制、按需启动。

建议性能预算：

| 模块 | 默认策略 | 性能要求 |
| --- | --- | --- |
| 唤醒词/VAD | 端侧低功耗运行 | 常驻但低 CPU、低电量消耗 |
| ASR/LLM/TTS | 唤醒或交互时启动 | 支持流式，首响应快 |
| 记忆蒸馏 | 本地后台低优先级 | 充电、空闲、非低电量时优先执行 |
| 向量索引 | 小型索引、摘要级向量化 | 不对全部原始消息建索引 |
| 场景音分类 | 短窗口、低频率 | 只输出标签，不长期保存原始音频 |
| 摄像头视觉 | 用户确认后单帧 | 不持续视频分析 |
| 智能关怀评估 | 事件驱动 + 低频轮询 | 不频繁唤醒系统 |

性能保护策略：

- 低电量、发热、内存紧张、用户正在游戏/导航/视频通话时，暂停记忆整理和画像蒸馏。
- 优先使用摘要和结构化画像，避免每次对话加载大量历史原文。
- 音频链路采用流式处理和短缓冲，减少等待和内存占用。
- TTS 常用短句可本地缓存，减少重复生成。
- 默认不开启摄像头、长时间录音或高频传感器采样。
- 所有重任务都应可取消、可延后、可在设置中关闭。

### 3.7 操作简洁原则

为了保证高质量但不复杂，交互应遵循：

- 新用户只需完成三步：选择 AI 角色、配置模型 API 或选择本地模型、授予必要权限。
- 权限按场景申请，不在首次启动时一次性索要所有权限。
- 高级能力隐藏在设置中，例如完整记忆模式、摄像头视觉、手表数据、主动关怀强度。
- 关键状态可视化：正在听、正在思考、正在说话、是否连接蓝牙、是否启用关怀。
- 一键暂停 AI、一键清除本次对话、一键关闭主动关怀。

## 4. 用户自配模型 API 接入

### 4.1 本地模型网关

所有模型通过 App 内的本地 `Model Gateway` 调用，屏蔽不同供应商差异。网关运行在手机上，API Key 存在系统安全区/Keychain/Keystore 中，不经过自建服务器中转。

```text
Model Gateway
├── chat.completions
├── realtime.voice
├── embeddings
├── rerank
├── vision
├── tts
├── asr
└── safety.moderation
```

### 4.2 模型选择策略

- **实时语音**：优先低延迟模型，要求首 token 快、支持流式输出。
- **深度陪伴**：优先高质量推理和情绪理解模型。
- **记忆抽取**：使用成本较低但结构化输出稳定的模型。
- **用户画像蒸馏**：异步批处理，可使用中等成本模型。
- **隐私敏感内容**：优先本地模型；如需外部 API，先脱敏、截断，并由用户授权。

### 4.3 模型路由示例

```json
{
  "task": "companion_chat",
  "latency_level": "low",
  "quality_level": "high",
  "privacy_level": "normal",
  "configured_providers": ["openai", "anthropic", "local"],
  "fallback": ["fast_small_model", "local_safety_reply"]
}
```

### 5.2 对话人格组装

每次对话动态组装：

```text
系统安全规则
+ 当前人格设定
+ 用户画像摘要
+ 最近会话摘要
```

### 5.3 AI 情绪值设计

为了让 AI 不像固定模板回复，每个 AI 角色维护一组“AI 情绪值”。这些值不是让 AI 真正拥有情绪，而是作为拟人化表达状态，用于影响语气、主动性、回复长度和安抚方式。

```json
{
  "ai_emotion_state": {
    "warmth": 0.82,
    "concern": 0.76,
    "playfulness": 0.35,
    "energy": 0.58,
    "closeness": 0.64,
    "worry": 0.42
  },
  "updated_by": ["user_emotion", "scene", "recent_memory", "relationship_stage"],
  "decay_policy": "slowly_return_to_persona_baseline"
}
```

回复时综合三类状态：

```text
AI 基础人格
+ AI 当前情绪值
+ 用户当前情绪/身体状态/场景
= 当前回复风格、语速、主动程度、是否追问
```

示例：

- 用户焦虑且心率偏高：提高 `concern`，降低 `playfulness`，回复更短、更稳、更安抚。
- 用户分享好消息：提高 `energy` 和 `playfulness`，语气更开心。
- 用户长时间没有回复且之前不舒服：提高 `concern`，触发低打扰关怀。
- 深夜场景：降低 `energy`，使用更轻、更慢、更安静的语音。

## 6. 场景智能分析

本地场景分析器输入：

- 时间：早晨、工作中、深夜、周末。
- 位置：家、公司、学校、通勤、陌生地点。
- 场景音：雨声、车流、人群、键盘声、厨房声、风声等，只做分类摘要，不长期保存原始音频。
- 设备：蓝牙耳机、车载蓝牙、智能手表、手机扬声器。
- 身体数据：心跳、心率、呼吸频率、脉搏、睡眠时长、压力、运动量。
- 摄像头单帧：仅在用户交互中确认授权后截取一帧，用于场景理解。
- 对话情绪：开心、焦虑、疲惫、愤怒、低落、孤独。
- 微信通道上下文：是否适合发语音、消息长度、用户是否正在忙。

输出：

```json
{
  "scene": "commuting_with_bluetooth_headset",
  "user_state": {
    "emotion": "tired",
    "confidence": 0.76,
    "body_signal": "high_heart_rate_after_poor_sleep"
  },
  "reply_mode": "voice",
  "voice_length": "short",
  "tone": "gentle_and_reassuring",
  "should_ask_followup": true
}
```


### 6.1 交互中摄像头授权与单帧视觉理解

AI 可以在自然对话中申请摄像头权限，但必须由用户明确确认。

示例：

```text
AI：你那边风景听起来很好看，我可以看一眼吗？
用户：可以
App：弹出系统摄像头权限或本次拍摄确认
用户确认
App：打开摄像头，仅截取一帧图片
视觉模型：分析画面摘要，例如“窗外有海、光线偏暗、用户可能在旅行”
AI：结合画面、位置、声音和对话上下文回复
```

安全边界：

- 默认不自动打开摄像头。
- 每次视觉理解都需要明确触发，支持“仅本次允许”。
- 优先截取单帧图片，而不是持续视频流，以降低隐私和算力压力。
- 图片分析后默认只保存结构化摘要；是否保存图片由用户单独授权。
- 涉及人脸、证件、屏幕隐私、儿童等敏感画面时应提示用户或拒绝分析。

### 6.2 场景音、位置、视觉、手表体征融合

高度拟人化回复来自多信号融合，但每种信号都要最小化采集。

```json
{
  "context_fusion": {
    "location": "seaside_walk",
    "ambient_sound": "wind_and_waves",
    "camera_frame_summary": "海边、傍晚、光线柔和",
    "wearable": {
      "heart_rate": 96,
      "respiratory_rate": 19,
      "pulse": 96,
      "confidence": 0.71
    },
    "user_emotion": "relaxed_but_tired",
    "reply_style": "gentle_observational_companion"
  }
}
```

回复示例：

> “海边风有点大，你心率也比平时高一点点。先别急着走太快，我们慢慢看会儿海，好吗？”

注意：心跳、呼吸频率、脉搏只能作为陪伴上下文，不输出医疗诊断。

## 7. 微信通道设计

### 7.1 通道能力

微信通道建议通过合规方式接入，例如公众号、企业微信、微信客服或小程序能力。通道层不直接侵入用户私人微信客户端，也不绕过平台规则。

### 7.2 回复方式决策

微信消息进入后，App 本地通道模块调用本地场景决策器：

```text
微信文本消息
    ↓
获取用户通道偏好、蓝牙状态、最近活跃设备
    ↓
判断是否适合语音回复
    ↓
文本回复或生成语音文件
    ↓
通过用户授权的微信通道发送
```

默认规则：

- 用户在微信通道内发内容，且无蓝牙耳机连接：默认文本回复。
- 用户在微信通道内发内容，且有蓝牙耳机连接：默认语音回复。
- 用户处于会议、深夜、公共外放风险场景：即使有蓝牙也可降级为文本。
- 用户明确说“发语音给我”：优先语音。
- 用户明确说“不方便听”：强制文本。

## 8. 记忆库设计

### 8.1 记忆分层

1. **原始事件层**
   - 保存必要的原始对话片段、语音转写、用户上传资料。
   - 可设置保留周期，支持用户删除。

2. **每日记忆层**
   - 每日异步蒸馏核心事件。
   - 记录日期、情绪、变化原因、重要人物、地点和主题。

3. **长期语义记忆层**
   - 保存跨日期稳定事实，如“用户喜欢夜跑”“用户讨厌被催促”。

4. **关系图谱层**
   - 连接不同日期、人物、地点、事件和情绪模式。

### 8.2 每日记忆结构

```json
{
  "memory_id": "m_2026_06_29_001",
  "user_id": "local_user",
  "date": "2026-06-29",
  "summary": "用户今天工作压力较大，晚上通过语音倾诉了项目延期带来的焦虑。",
  "core_events": [
    {
      "event": "项目延期导致焦虑",
      "importance": 0.88,
      "people": ["直属领导"],
      "location": "公司",
      "source_sessions": ["s_001", "s_002"]
    }
  ],
  "mood": {
    "primary": "anxious",
    "secondary": ["tired", "lonely"],
    "intensity": 0.72,
    "trend": "worse_than_yesterday"
  },
  "emotion_change_reasons": [
    "项目延期",
    "睡眠不足",

  ],

    }

```

### 8.3 跨日期记忆连接

当新每日记忆生成后，系统执行：

1. 生成 embedding。
2. 从向量库检索相似历史记忆。
3. 用 LLM 判断是否存在真实关联。
4. 创建边：`same_topic`、`same_person`、`emotion_pattern`、`cause_effect`、`progress_update`。
5. 更新用户画像。


### 8.4 手机端向量记忆库取舍

本项目没有自建服务器，因此完整记忆也必须留在用户手机上。但手机端不建议一开始就做“超大规模全量向量库”。推荐采用“本地分层记忆 + 小型向量索引 + 关键词/时间索引”的轻量方案。

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| 本地全量大向量库 | 离线完整、隐私强 | 占空间、耗电、索引维护复杂 | 后期高级模式 |
| 本地小型向量库 | 隐私强、检索快、可离线 | 容量有限，需要摘要压缩 | 默认方案 |
| 关键词 + 时间索引 | 极轻量、稳定 | 语义召回弱 | 与小型向量库组合 |

推荐端侧保存：

- 最近 7-30 天的会话摘要和每日记忆。
- 用户画像的结构化摘要。
- 当前 AI 人格配置与 AI 情绪基线。
- 关怀意图池和未完成提醒。
- 小型 embedding 索引：只对每日摘要、重要事件、稳定画像做向量化，不对所有原始消息建索引。
- 原始对话可按用户设置保留、加密、定期压缩或删除。

如果用户担心空间占用，可提供三档：

```text
轻量模式：只保存摘要、画像、最近少量消息
标准模式：保存摘要 + 重要消息 + 小型向量索引
完整模式：保存较多原始对话 + 更大本地向量索引
```

所有记忆、画像、向量索引、文件和权限记录默认只在手机本地。外部模型 API 只接收当次生成所需的最小上下文。

## 10. 蒸馏用户数据与人格

### 10.1 蒸馏目标

用户发送的数据可以蒸馏为：

- 稳定偏好：喜欢什么语气、什么回复长度、什么陪伴方式。
- 情绪模式：什么时候容易焦虑、低落、兴奋。
- 行为节奏：作息、运动、工作高压周期。
- 关系网络：重要人物及其情感影响。
- 个性特征：表达方式、价值观、边界偏好。
- AI 人格适配参数：更适合温柔型、理性型、幽默型还是主动型陪伴。

### 10.2 蒸馏流水线

```text
用户输入/语音转写/设备信号
    ↓
隐私过滤与脱敏
    ↓
事件抽取
    ↓
情绪与原因识别
    ↓
长期偏好识别
    ↓
画像更新
    ↓
人格适配建议
    ↓
可解释变更记录，允许用户查看和删除
```

### 10.3 人格自适应

系统不应擅自大幅改变 AI 人格，而是通过小幅参数调整提升陪伴体验：

```json
{
  "suggested_persona_adjustment": {
    "empathy": "+0.05",
    "directness": "-0.10",
    "humor": "no_change",
    "reason": "用户最近在压力场景下对温柔安抚响应更好"
  },
  "requires_user_confirmation": true
}
```

## 11. 本地实时语音交互

### 11.1 目标体验

- 用户说话时，AI 可以实时理解。
- AI 说话时，用户可以随意打断。
- 首句响应尽可能低延迟。
- 回复可先短后长：先给情绪回应，再补充具体建议。

### 11.2 推荐流程

```text
麦克风音频流
    ↓
VAD 检测是否有人声
    ↓
流式 ASR
    ↓
会话编排器
    ↓
流式 LLM
    ↓
句子级 TTS
    ↓
本地播放器
```

### 11.3 打断机制

- 客户端持续运行低功耗 VAD。
- 检测到用户打断后立即停止 TTS 播放。
- 向本地会话编排器发送 `barge_in` 事件。
- 本地会话编排器取消当前生成任务；如果正在调用外部模型 API，则中断流式请求，并把已播放文本写入会话状态。
- 新一轮对话携带“用户打断了上一句”的上下文。

## 12. 本地语音生成

为保证轻量化：

- 常规高质量 TTS 可由用户配置的外部 TTS API 生成；隐私模式下使用本地 TTS。
- 常用短句、情绪反馈、唤醒语可在本地缓存。
- 高隐私模式可使用端侧轻量 TTS。
- MVP 阶段固定两种核心音色：男声一个、女声一个；女声优先提供台湾话/台湾口音版本。每个人格可在固定音色基础上配置语速、停顿、情绪强度。

TTS 输出建议分层：

```json
{
  "voice_id": "female_taiwan_warm_01",
  "speed": 0.95,
  "pitch": 1.02,
  "emotion": "gentle",
  "breathiness": 0.2,
  "pause_style": "natural",
  "available_voices": ["male_standard_01", "female_taiwan_warm_01"]
}
```

## 13. 本地数据存储建议

由于没有自建服务器，数据层应全部在手机本地实现：

- **SQLite**：用户、会话、消息、权限记录、画像、关怀意图、AI 情绪状态。
- **本地向量索引**：可使用 sqlite-vec、sqlite-vss、FAISS mobile、ObjectBox Vector 或平台可用的轻量向量方案。
- **本地图谱表**：用 SQLite 表保存记忆之间的关系边，例如 `memory_links`。
- **本地文件库**：语音、图片单帧、用户上传文件，默认加密保存。
- **系统安全区**：模型 API Key、加密密钥、微信通道凭据应放入 iOS Keychain 或 Android Keystore。
- **本地任务队列**：每日记忆总结、画像蒸馏、关怀意图评估、过期数据清理。

建议所有本地数据库都支持：

- 用户一键导出。
- 用户一键删除。
- 按数据类型清理：语音、图片、原始聊天、摘要、画像。
- 端侧加密。
- 低电量、发热、弱网时暂停重任务。

## 14. 安全、隐私与合规

此类 App 涉及位置、麦克风、文件、身体数据和微信交互，必须采用强隐私设计：

- 权限按需申请，不一次性索要全部权限。
- 明确解释每个权限用途。
- 用户可关闭位置、手表、文件、微信通道、记忆蒸馏。
- 用户可查看、编辑、导出、删除记忆和画像。
- 身体数据只做情绪和陪伴辅助，不做医疗诊断。
- 高风险情绪场景提供支持性回复和求助建议。
- 敏感数据在本地加密存储，调用外部 API 时使用 TLS。
- 调用用户配置的外部模型 API 前做脱敏、截断和最小化传输。
- 微信通道必须遵守平台规则和用户授权。

## 19. 工程实现原则

- 无自建服务器：语音唤醒、VAD、实时音频、设备状态、播放控制、记忆、画像、向量索引、关怀意图和权限审计都在手机本地；外部模型 API 只负责当次推理。
- 同时支持 Android、iOS 和 HarmonyOS：共享业务核心，平台能力使用原生适配，避免为了跨平台牺牲音频、蓝牙、健康数据和权限体验。
- 性能优先：任何后台监听、记忆整理、画像蒸馏、向量索引更新和场景分析都必须低功耗、可暂停、可降级、可关闭。
- 所有模型能力走本地模型网关，避免业务层绑定某一家模型，也方便用户自行更换 API。
- 所有本地记忆写入都要可解释、可撤销、可删除。
- 场景决策必须可回溯，记录为什么选择文本或语音。
- AI 人格必须有边界，不鼓励用户形成不健康依赖。
- 任何身体数据分析都只能作为陪伴上下文，不输出诊断结论。
- 操作保持简洁：默认只展示核心聊天、语音、角色和权限入口，高级能力放入设置页逐步开启。
